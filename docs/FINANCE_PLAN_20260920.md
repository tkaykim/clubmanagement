# 원샷크루 프로젝트 예산·개인 정산·재무 조회 계획

작성일: 2026-09-20.
상태: 계획 수립 완료, 구현·운영 반영 전.
사용자 확정: 프로젝트 담당자도 담당 프로젝트 전체 참여자의 수당을 조회하고 배분한다.

> 아래는 최초 계획의 보존본이다.
> 구현된 운영 절차와 현재 경계는 `FINANCE_OPERATIONS.md` 및 실제 migration/API를 기준으로 확인한다.
> 재무 담당자는 기존 일정 담당 테이블을 재사용하지 않고 별도 `finance_project_managers`로 구현했다.
> 은행 이체 실행, 계산서 자동 발행, grigo-artist·ERP·Clobe의 상시 자동 동기화는 이번 앱 기능에 포함하지 않는다.

## 1. 목표와 범위

원샷크루 앱에서 대표, 재무담당자, 프로젝트 담당자, 참여자가 동일한 프로젝트와 정산 기록을 각자의 권한으로 확인한다.
프로젝트 담당자는 활성 원샷크루 멤버 중 지정하며 새 프로젝트의 기본 담당자는 대장이다.
김현준 대표와 명시적으로 지정된 재무담당자는 원샷크루 전체 프로젝트 재무를 조회한다.
원샷 운영진이라는 이유만으로 재무 권한을 부여하지 않는다.
이번 산출물은 구현 계획이며 실제 계정 권한, 금액, 지급 상태, 배포는 변경하지 않는다.

## 2. 확정된 접근 정책

| 정보·작업 | 김현준 대표 | 재무담당자 | 해당 프로젝트 담당자 | 미배정 운영진·일반 참여자 |
|---|---|---|---|---|
| 프로젝트 총예산·계약금액·수금·잔여예산 | 전체 | 전체 | 담당 프로젝트 | 비공개 |
| 참여자별 세전 수당·공제액·실지급액 | 전체 | 전체 | 담당 프로젝트 전체 | 본인 확정 내역만 |
| 수당 배분안 작성 | 전체 | 전체 | 담당 프로젝트 | 불가 |
| 총예산·집행한도 확정 및 증액 | 전체 | 전체 | 변경 요청 | 불가 |
| 수금 증빙·지급 결과 등록 | 전체 | 전체 | 결과 조회 | 본인 지급 결과 조회 |
| 담당자 지정·변경 | 가능 | 가능 | 변경 요청 | 불가 |
| 개인 계좌·세무 서류 | 별도 민감정보 권한 | 업무상 필요한 범위 | 제출 완료 여부만 | 본인 정보 |
| 정산 다운로드 | 전체 | 전체 | 담당 프로젝트 | 본인 내역만 |

대표와 재무담당자는 담당자 배정 여부와 관계없이 전 프로젝트를 조회하는 명시적 예외다.
대장도 기본 배정된 프로젝트에 대해서만 담당자 권한을 가지며, 다른 사람에게 담당자를 넘긴 프로젝트의 예산에는 접근하지 못한다.
대표 권한을 기존 owner 전체에 부여하지 않고 검증된 김현준 인증 계정에만 연결한다.
재무 권한은 원샷 운영진 등급과 별개이며 재무 사용자가 공연 멤버로 가입하거나 명단에 공개될 필요가 없다.
금액이 없는 참여 명단과 일정은 기존 운영 권한을 유지하되 계약서·수당 협의 메모는 재무 문서로 분리한다.

### 배정·회수 규칙

- 기존 project_managers를 재사용하되 일정 조회 담당과 재무 담당을 명시적으로 구분한다.
- 기본 담당자는 설정에 저장한 리더의 crew_member ID로 배정하고 이름·예명 문자열로 추정하지 않는다.
- 기존 project_managers 행에는 재무 권한을 자동 부여하지 않는다.
- 신규 프로젝트의 기본 담당자 배정은 프로젝트 생성과 같은 트랜잭션으로 처리한다.
- 기본 리더가 없거나 비활성이면 담당자 미배정으로 저장하고 대표·재무 화면에 보완 항목을 표시한다.
- 재무 담당자 배정·권한 변경 API도 제한하여 미배정 운영진의 본인 배정을 통한 권한 상승을 막는다.
- 담당자 변경 즉시 이후 API·DB 조회와 캐시 접근에서 전 담당자의 권한을 회수한다.
- 담당자 해제 후에도 본인이 참여해 확정받은 정산 내역은 계속 조회할 수 있다.
- 이미 다운로드한 파일은 회수할 수 없으므로 내려받기 기록을 남긴다.

## 3. 금액의 의미

화면에 총예산과 고객 계약금액을 각각 저장하되 생성 시 고객 공급가액을 총예산 기본값으로 제안한다.
총예산은 해당 프로젝트에 배정된 집행 한도이며 고객 계약금액과 달라질 수 있다.
공급가액, 부가세, 고객 청구합계, 실제 수금액을 구분한다.
미입력 금액은 null로 저장하고 확정된 0원과 구분한다.

| 항목 | 의미 |
|---|---|
| 고객 계약금액 | 고객에게 청구할 공급가액, VAT·통화 별도 |
| 총예산 | 행사에 배정한 집행 한도, 기본 KRW·VAT 제외 기준 |
| 배정 비용 | 확정된 세전 수당 합계와 기타 비용의 예산 반영액 |
| 미배정 예산 | 총예산에서 배정 비용을 뺀 금액 |
| 세전 수당 | 개인에게 약정한 보수, 항목별 합계 |
| 공제액 | 개인에게 적용되는 세무 방식으로 산출한 원천세 |
| 실지급 예정액 | 확정 세전 수당에서 공제액을 뺀 금액 |
| 실지급 누계 | 실제 이체 증빙으로 확인한 개인 지급액 |
| 미지급액 | 실지급 예정액에서 실지급 누계를 뺀 금액 |
| 미수금 | 확정 청구합계에서 확인된 고객 입금 배부액을 뺀 금액 |

원천세를 공제해도 세전 수당 전체가 인건비이며 공제액은 회사 이익이나 남는 예산이 아니다.
원천세 납부는 멤버 실지급과 별도 현금 유출로 추적하고 인건비에 두 번 더하지 않는다.
실비 정산, 매입 VAT, 송금 수수료는 항목별로 저장하고 수당과 동일한 세율을 무조건 적용하지 않는다.
외화 거래는 원통화 금액과 적용 환율·원화 환산액을 보존하며 통화가 다른 금액을 바로 합산하지 않는다.

### 3.3% 계산

국내 원천징수 대상 사업소득의 기본 계산은 소득세 3%와 지방소득세 0.3% 공제를 사용한다.
예시: 세전 300,000원, 공제 9,900원, 실지급 예정액 290,100원.
실제 송금 전에는 받은 금액을 0원으로 표시하고 290,100원을 지급 예정액으로만 표시한다.
사업자 세금계산서·외국인 등 다른 세무 유형은 별도 모드로 두며 재무담당자가 적용 유형을 확정한다.
정산 확정 시 세전액, 과세 기준액, 세율, 세목별 공제액, 절사 정책 버전, 실지급 예정액을 스냅샷으로 보존한다.
기존 grigo-artist와 deetz는 반올림·절사 방식이 다르므로 이미 확정된 과거 금액을 새 계산식으로 재산출하지 않는다.
구현 단계에서 재무 원장과 대조한 원단위 계산 기준을 고정하고 UI·API·CSV가 같은 서버 계산기를 사용한다.
한 수당을 나누어 지급해도 이미 확정한 공제액을 다시 공제하지 않는다.

## 4. 사용자 화면

### 대표·재무: 프로젝트 재무 목록

한 행에 프로젝트명, 행사일, 담당자, 총예산, 고객 청구액, 수금 누계, 미수금, 세전 수당 합계, 실지급 누계, 미지급액, 상태를 표시한다.
프로젝트·월·담당자·거래처·참여자·수금상태·지급상태로 필터링한다.
예정일 없는 미지급과 금액 미확정 건도 별도 보완 목록에 포함한다.
날짜 필터는 행사일·입금일·지급일을 구분하며 월 합계와 내려받기에 같은 기준을 적용한다.
프로젝트 상세는 예산, 고객 청구·입금, 참여자별 정산, 기타 지출, 변경 이력으로 구성한다.

### 프로젝트 담당자: 담당 프로젝트 재무

기존 내 담당 프로젝트에서 예산과 정산 탭으로 진입한다.
상단에는 총예산, 배정 비용, 미배정 예산, 수금·지급 진행을 표시한다.
참여자 표에는 이름, 역할, 참여일, 수당 항목, 세전액, 공제액, 실지급 예정액, 지급 누계, 예정일, 상태를 표시한다.
여러 사람에게 같은 수당을 넣는 일괄 입력과 사람별 수정·추가 항목을 제공한다.
리더 수당, 리허설, 본공연, 촬영, 교통비 등 사유를 항목으로 남긴다.
담당자는 배분안을 저장하고 재무 검토로 제출한다.
총예산을 초과하는 배분안은 초과액을 표시하고 예산 조정이 끝날 때까지 확정을 막는다.
동시에 수정한 다른 사용자의 변경은 버전 충돌로 알려 덮어쓰지 않는다.

### 참여자: 내 정산

기존 마이페이지 정산을 프로젝트별 내역으로 확장한다.
프로젝트명, 참여일·역할, 본인 수당의 항목과 사유, 세전액, 공제액, 실지급 예정액, 지급 누계, 지급일·예정일, 남은 금액을 보여준다.
상단에는 정산 확정 대기 건수, 확정 미지급액, 선택 기간에 실제 받은 금액을 표시한다.
공개 전 배분안의 금액은 보여주지 않고 정산 확정 대기로만 표시한다.
연도·월·프로젝트별 조회와 본인 내역 다운로드를 제공한다.
행사가 취소되거나 종료돼도 본인의 확정·지급 이력은 보존한다.
총예산, 회사 잔액, 고객 계약서, 다른 사람의 수당, 개인별 액수를 역산할 수 있는 팀 합계를 응답에 포함하지 않는다.

## 5. 재무 업무 흐름

1. 대표·재무가 프로젝트의 계약금액·총예산·담당자·수금 조건을 등록한다.
2. 담당자가 실제 투입 인원과 수당·사유를 입력해 배분안을 제출한다.
3. 재무가 예산, 대상자, 세무 유형, 지급 정보와 예정일을 검토해 정산을 확정한다.
4. 확정된 개인 내역을 본인에게 공개하고 앱 알림은 금액 없이 로그인 화면으로 연결한다.
5. 재무가 실제 이체를 진행한 뒤 거래 증빙을 연결한다.
6. 프로젝트·개인 화면의 지급 누계와 미지급액이 같은 원장으로 갱신된다.
7. ERP·Clobe 및 필요한 아티스트 월 정산 연결을 대조해 마감한다.

수당 확정은 draft → submitted → confirmed로 관리한다.
반려는 사유와 함께 초안으로 되돌리고 확정 후 수정은 새 버전과 차액 이력을 남긴다.
지급 상태는 not_paid, partially_paid, paid로 실제 이체 배부 합계에서 계산한다.
처리중·실패·취소된 이체는 실제 지급액에 더하지 않는다.
지급이 끝난 기록은 덮어쓰거나 삭제하지 않고 반제·추가 정산으로 정정한다.
고객 수금과 개인 지급은 각각의 약정 기한을 따르며 고객 미입금을 이유로 개인 지급일을 자동 변경하지 않는다.

## 6. 재무의 “누구에게, 무엇 때문에, 얼마” 추적

입금 한 건에는 거래처, 프로젝트, 청구서·계산서 참조, 금액·통화, 실제 입금일, 거래 증빙을 연결한다.
출금 한 건에는 수취인, 프로젝트, 정산 식별자, 수당 사유, 금액·통화, 실제 지급일, 이체 증빙을 연결한다.
한 번의 이체로 여러 프로젝트를 지급했거나 한 프로젝트를 여러 번 지급한 경우 배부행으로 연결한다.
배부액 합계가 실제 은행 거래액을 넘지 않도록 검증한다.
확정 의무금액을 넘기는 지급 연결은 차액 정산 또는 선지급 사유가 있을 때만 별도로 처리한다.
은행 거래에는 계좌별 원천 거래 식별자를 저장해 같은 이체를 중복 등록하지 못하게 한다.
증빙이 없는 항목은 확인 필요로 표시하고 송금 실패를 지급완료로 바꾸지 않는다.
프로젝트와 무관한 거래, 이름만 유사한 거래를 자동 배부하지 않는다.
재무용 내보내기는 프로젝트·수취인·역할·사유·세전·세목별 공제·실지급·거래일·증빙 참조를 포함한다.

## 7. 데이터·연동 설계

아래 이름은 구현 단계의 제안이며 마이그레이션은 아직 만들지 않는다.

| 데이터 | 설계 방향 |
|---|---|
| projects | 기존 행사 정보 유지, 공용 금액 필드에 비공개 예산·개인 수당 저장 금지 |
| project_managers | 기존 지정 재사용, 재무 범위·주담당·변경 이력 추가 |
| finance_access_grants | 원샷 범위의 대표·재무 권한을 검증된 인증 계정에 명시적으로 부여 |
| project_finance | 비공개 총예산·집행한도·통화·ERP 연결키·버전 |
| payouts와 지급 항목 | 기존 행 ID 유지, 개인 수당 항목·공제 스냅샷·확정 상태·원천 연결 확장 |
| 지급 실행·배부 | 실제 지급 원천 거래와 정산행의 연결, 부분·합산 지급 지원 |
| 재무 읽기모델 | ERP 청구·비용 및 Clobe 실제 거래를 ID로 연결한 조회용 투영 |
| 비공개 변경 이력 | 행위자·시각·변경 전후·사유·확정 버전, 일반 활동 로그와 분리 |

원샷크루가 사용자 화면과 신규 개인 수당 합의의 정본을 맡고 고객 청구·입금은 ERP·Clobe의 기존 기록을 연결한다.
앱에서 입력한 재무 지시는 기존 orchestrator 쓰기 경로로 ERP에 반영하고 성공 여부·원천 ID·마지막 확인 시각을 보여준다.
실패·재시도 작업은 동일 명령 ID를 사용해 중복 청구·중복 비용을 막는다.
조회용 복사본을 별도 수정 가능한 두 번째 장부로 만들지 않는다.
권한을 확인한 서버가 외부 자료에서 허용된 필드만 추려 반환하며 멤버 브라우저에 외부 서비스 관리자 키를 보내지 않는다.
배치 조회의 페이지 제한과 필터를 공통화해 화면·합계·CSV가 같은 대상을 계산하도록 한다.

### 기존 deetz·grigo-artist 지급 건

9월 14일 business_udong에는 실지급을 deetz로 우회하는 임시 운영 메모가 있다.
한편 전속 아티스트 정산 정본에는 원샷크루 기원 건과 grigo-artist 월 정산 연결 원칙이 별도로 있다.
따라서 사람의 소속만으로 과거 지급 건을 자동 이동하지 않는다.
전환 점검표에서 건마다 원샷 프로젝트 ID, 개인 계정 ID, 외부 정산 ID, 실제 지급 원장을 확인한다.
기존 외부 지급 건은 source_system/source_id를 가진 읽기 연결로 원샷크루 내 정산에 표시한다.
각 정산 건의 지급 상태를 수정하는 시스템은 하나로 고정한다.
deetz 잔액 출금 건은 settlements.status가 아니라 실제 withdrawal·배부 원장을 읽는다.
grigo-artist에는 원샷 정산 식별자를 연결하고 프로젝트 고객 매출이나 개인 비용을 중복 합산하지 않는다.
신규 건의 원샷 지급 원장을 활성화할 때 기존 시스템의 동일 건 신규 지급 생성을 함께 차단한다.

## 8. 정보 노출 방지

화면에서 탭을 숨기는 것만으로 권한을 구현하지 않는다.
비공개 예산은 공용 projects와 물리적으로 분리하고 개인 정산은 수취인 단위로 보호한다.
기존 운영진 전체 허용 정책과 API 가드를 새 정책으로 교체하며 제한 정책을 추가하는 데 그치지 않는다.
서버 API, DB RLS·GRANT, SSR 데이터, CSV, 집계 RPC, 첨부 다운로드, 알림, 검색·로그를 함께 점검한다.
권한 없는 응답에서는 금액 필드를 0으로 가리기보다 아예 제외한다.
프로젝트 ID·수취인 ID 바꿔치기, 다른 멤버의 URL 접근, 직접 DB API 조회를 각각 차단한다.
정산 파일은 비공개 저장하고 재조회마다 권한을 확인하는 다운로드 경로를 사용한다.
일반 활동 로그나 잠금화면 푸시에 개인 수당이나 총예산을 남기지 않는다.
캐시는 사용자·권한·프로젝트 범위로 격리하거나 비공개 재무 응답에 공용 캐시를 사용하지 않는다.
신규 재무 권한과 기존 운영 권한은 별개여서 운영진이 자신의 역할·담당 범위를 조작해 재무를 열 수 없어야 한다.

## 9. 구현 순서와 완료 기준

### 1단계: 권한·비공개 금액 구조

대표·재무 별도 권한, 대장 기본 배정, 담당자 변경, 비공개 예산 테이블과 RLS를 먼저 구현한다.
프로젝트 생성·수정에서 fee를 승인자 전원에게 자동 복사하는 경로를 폐기하고 기존 지급행 ID를 보존한다.
공개 페이지·메일·피드가 예산·개인 수당을 다시 노출하지 않게 공용 금액 소비처를 전수 교체한다.
완료 기준은 미배정 운영진을 포함한 권한별 직접 API·DB 접근 테스트 통과다.

### 2단계: 개인별 수당 배분·내 정산

담당자 일괄 입력과 개인 수정, 항목별 사유, 세금 계산, 재무 확정, 본인 정산 내역을 구현한다.
금액 미확정과 무보수 0원을 구분하고 예정일 없는 건도 보완 목록에 보이게 한다.
완료 기준은 담당자 배분부터 재무 확정, 참여자 본인 조회까지 같은 금액으로 이어지는 E2E 통과다.

### 3단계: 수금·실지급·재무 목록

ERP 청구 연결, 실제 입금·출금 증빙 연결, 합산·부분 지급 배부와 재무 CSV를 구현한다.
기존 재무 할일 경로를 재사용하고 finance@ 지시에는 프로젝트 식별자와 재무 화면 링크를 연결한다.
완료 기준은 프로젝트와 개인의 지급 합계가 동일 증빙과 일치하고 재시도 시 중복 기록이 없다는 검증이다.

### 4단계: 과거 이력 연결·전환

기존 0원 행은 금액 미확정 후보로 검토하고 무료·유료 여부를 사람별·건별 근거 없이 일괄 추정하지 않는다.
원천 지급 증빙이 없는 과거 내역을 지급완료로 만들지 않는다.
기존 외부 정산·계정 매핑을 검증한 뒤 읽기 연결하고 이력 합계를 대조한다.
신규 프로젝트 한 건으로 대표·재무·담당자·일반 멤버·미배정 운영진 역할을 검증한 후 적용 범위를 넓힌다.
배포가 되돌려져도 예산·개인 수당 차단 정책은 유지하며 구 UI에 재무 데이터를 다시 노출하지 않는다.

### 필수 인수 시나리오

1. 대표·재무 권한이 없는 미배정 admin/owner와 일반 멤버는 화면·JSON·DB·CSV 어디에서도 총예산을 조회하지 못한다.
2. 담당자 A는 본인 프로젝트만 조회·배분하고 다른 담당자의 프로젝트는 조회하지 못한다.
3. 담당자 변경 뒤 A의 다음 요청은 차단되고 B는 같은 예산·정산 내역을 이어서 확인한다.
4. 대장은 신규 프로젝트에 기본 배정되지만 수동으로 다른 사람에게 배정한 프로젝트는 예외로 유지한다.
5. 일반 멤버는 확정된 본인 내역만 조회하고 동료의 수당·팀 합계는 얻지 못한다.
6. 세전 300,000원 표준 예시에서 공제 9,900원과 예정액 290,100원이 모든 화면·CSV에 일치한다.
7. 100,000원을 먼저 지급하면 실지급 100,000원, 미지급 190,100원이며 완납 때만 지급완료다.
8. 같은 증빙을 두 번 등록해도 지급 누계가 증가하지 않고 실패한 이체는 합계에서 제외된다.
9. 2명이 동시에 금액을 수정하면 오래된 버전의 저장이 거부되고 기존 확정본이 보존된다.
10. 외부 원장에 지급된 건을 연결하면 본인의 받은 금액에 한 번만 반영된다.
11. 프로젝트 예산 4,000,000원과 5인 각 수당 300,000원은 수당 총액 1,500,000원으로 집계된다.
12. 1,000건을 넘는 원장·날짜 없는 미확정 건·연도 경계·부분 지급을 포함해 화면과 CSV 합계가 일치한다.

## 10. 검토 근거와 계획의 한계

현재 코드의 requireAdmin과 getProjectAccess는 운영진 권한을 재무 권한과 분리하지 않는다.
project_managers는 이미 있으나 프로젝트 읽기 전용 용도로 설계돼 있다.
관리자 정산 CSV도 requireAdmin을 사용하므로 화면과 함께 교체해야 한다.
현재 담당자 화면은 공통 관리 컴포넌트에 readOnly를 전달하므로 서버 응답 필드 제한을 별도로 구현해야 한다.
이번 점검은 로컬 코드·공유 정본·공식 문서 검토이며 9월 20일 운영 잔액과 인원수 전수 대사는 수행하지 않았다.
실제 재무 사용자와 대장 계정의 ID, 건별 외부 원장 연결은 구현 착수 시 운영 자료로 확인한다.
